## Advanced Documents Capabilities

In <<advanced-client-api>> we talked about advanced client API usage in RavenDB and in <<documents-extensions>> we covered other types of data that you can store in RavenDB, such as attachments, 
counters, time series and revisions. In this chapter, we are going to cover more advanced capabilities that RavenDB offers, at the database side. This covers features in which RavenDB itself
is operating on your documents, without any nudges from the client side.

This isn't going to be a long chapter, as most of these features we discuss are straightforward and meant to address specific scenarios. They are very useful in many scenarios, so it 
is important to know about them.

### Document Expiration

Sometimes, a document comes with an expiration date. For example, you may want to store a `ResetPasswordLink` document that is only valid for 30 minutes. After that, it should be removed.
You can handle the validity period by checking the date of the document when the user click on the link, but what if they never do? How do you clean up the data after the time expired? 
You can write a task that would check for `ResetPasswordLink` documents that are too old and delete them. Then you'll need to schedule that task to run periodically, monitor it, etc.

RavenDB comes with a builtin expiration mechanism that can take care of this for you. You just need to mark the documents that you want to expire with a special metadata field (`@expires`), 
and RavenDB will take care of the rest for you. You can see how to mark a document as expirable in <<set-document-expiration>> using the `@expires` metadata field.

[[set-document-expiration]]
.Set the expiration data on a document. 
[source, csharp]
----
using (var session = store.OpenSession())
{
    var token = Guid.NewGuid().ToString();
    var link = new ResetPasswordLink("users/1-A", token); 
    session.Store(link);
    var metadata = session.Advanced.GetMetadataFor(link); <1>
    var expires = DateTime.UtcNow.AddMinutes(30)
        .ToString("O");                                   <2>
    metadata["@expires"] = expires;                       <3>
    session.SaveChanges();
}
----
<1> Get the metadata for the newly stored reset link document.
<2> Expiration uses UTC date in ISO 8601 format (`yyyy-MM-ddTHH:mm:ss.fffffffZ`).
<3> Set the `@expires` metadata field to the desired expiration date.

The code in <<set-document-expiration>> will create a `ResetPasswordLink` document that will expire in 30 minutes. Note that for expiration, we _must_ always use UTC time, not local time.
RavenDB will automatically delete the document after that time passes, so you don't have to do anything else. Well, almost...
If you'll run the code in <<set-document-expiration>> without enabling expiration on the database, you'll see the warning in the Studio shown in <<expiration-when-not-enabled>>.

[[expiration-when-not-enabled]]
.The Studio warns about setting expiration when it is not enabled
image::./Ch06/img01.png[]

By default, expiration needs to be _explicitly enabled_ on the database side. You can do that using the Studio, or by using the `ConfigureExpirationOperation` operation using the API.
In the RavenDB Studio, go to the `Settings`` tab of your database, and then to the `Document Expiration` section, as shown in <<enable-expiration-in-studio>>, enable
`Enable Document Expiration` and click on `Save`.

[[enable-expiration-in-studio]]
.Enabling expiration in the Studio
image::./Ch06/img02.png[]

After enabling expiration on the database, the documents that you marked for expiration will be automatically deleted after their expiration date passes. Note the options you can see
in <<enable-expiration-in-studio>>: you can set the frequency in which RavenDB will check for expired documents (the default is every 60 seconds). In other words, if a document expires 
at `12:00:00`, it will be deleted at some time around that time (based on the frequency you set and how many other documents you have that also needs to be expired.

I mention that because in some instances you may have a _lot_ of documents set to expire at a given point in time. For example, you may have a promotional offer to all your customers
that all expire at midnight on a given day. In that case, you may have millions of documents to expire at once. This is also why you have the option to set the batch size in
<<enable-expiration-in-studio>>. Instead of having to immediately delete all expired documents, RavenDB will delete them in batches, allowing it to control the amount of load that it 
has to deal with all at once.

.Documents expiration in a cluster
****
When running in a cluster, with multiple nodes hosting the same database, how does RavenDB handles expiration?.
Running expiration on multiple nodes at the same time would be inefficient and could lead to conflicts. To avoid that, expiration is handled by the database leader node. The expiration 
task will run only on the leader, and the deletions will be replicated to the other nodes. You'll learn more about the distributed nature of RavenDB in <<ravendb-clusters>>.
****

The practical impact of this behavior is that you should not rely on expiration to happen at an _exact_ time. RavenDB does the expiration check periodically and in batches, so there may 
be a delay between the expiration time and the actual deletion of the document. In practice, however, that doesn't usually matter. If an expiration link was set with expiration and lasted
for 30 minutes or 30 minutes and 40 seconds, it is fine. Same for a promotional offer that lasted for a few extra minutes after midnight before being deleted. 
If you do care about the exact time of expiration, you should also check that that in your application logic as well. 

### Refreshing Documents

In addition to expiring documents using `@expires`, RavenDB also supports refreshing documents using the `@refresh` metadata field. The refresh mechanism is similar to expiration, but 
instead of deleting the document, it will update the document to remove the `@refresh` metadata field when the time comes. That is all it does. We'll first take a look at how this works
and then we'll discuss _why_ this is useful. Let's see how to set the `@refresh` metadata field on a document in <<set-document-refresh>>.

[[set-document-refresh]]
.Set the refresh data on a document.
[source, csharp]
----
using (var session = store.OpenSession())
{
    Survey survey = new Survey
    {
        Title = "Customer Satisfaction",
        Questions =
        [
            "How satisfied are you with our product?",
            "How likely are you to recommend our product to others?"
        ]
    };
    session.Store(survey);
    var metadata = session.Advanced.GetMetadataFor(survey); <1>
    var refresh = DateTime.UtcNow.AddDays(3).ToString("O"); <2>
    metadata["@refresh"] = refresh;                         <3>
    session.SaveChanges();
}
----
<1> Get the metadata for the newly stored survey document.
<2> Refresh uses UTC date in ISO 8601 format (`yyyy-MM-ddTHH:mm:ss.fffffffZ`).
<3> Set the `@refresh` metadata field to the desired refresh date.

Running the code in <<set-document-refresh>> will create a `Survey` document that will be refreshed in 3 days. You can see how that document will look in the Studio 
in <<refresh-doc-studio>>.

[[refresh-doc-studio]]
.A survey document with the @refresh metadata field set
image::./Ch06/img03.png[]

After 3 days pass, RavenDB will automatically update the document to remove the `@refresh` metadata field, as shown in <<refreshed-doc-studio>>.

[[refreshed-doc-studio]]
.The survey document after being refreshed
image::./Ch06/img04.png[]

Note that in <<refreshed-doc-studio>>, the document is otherwise unchanged. Only the `@refresh` metadata field was removed.

You might be wondering about why this feature even exists. The refresh feature is meant to be used in conjunction with other RavenDB features, 
not on its own. The actual point of using `@refresh` is to trigger _other parts_ of RavenDB, which act on document modification. You'll see an example of how
we can use `@refresh` in <<batch-processing>>, we we use it to trigger processing of documents using subscriptions at a given time.

RavenDB has quite a number of features that are triggered by document modifications, such as indexing, subscriptions, ETL, AI integration, and more. By using 
`@refresh`, we can schedule things so that they will happen at a given time in the future, without having to have an external process to do that for us.

.Refresh is one-shot only
****
The `@refresh` metadata field is removed at the scheduled time, so it is a one-shot operation. If you want to have a recurring refresh, you'll need to 
set the `@refresh` field again. There is no way to set a recurring refresh in RavenDB.
****

In almost all respects, the `@refresh` mechanism is similar to the `@expires` mechanism. The `@refresh` feature also needs to be explicitly  enabled on the database side, 
and both features run on the primary database node and replicate the changes to the other nodes in a cluster. You can enable the `@refresh` feature in the Studio, by going to 
the `Settings` tab of your database and then to the `Document Refresh` section or using `ConfigureRefreshOperation` API.

On its own, the `@refresh` feature is useless, but when combined with other RavenDB features, it becomes very powerful mechanism to schedule work to be done at a later time.

### Archiving Documents

Once your database hits a certain size, you need to start thinking about what exactly you are _doing_ with all this data. In many cases, you may have documents that are no 
longer actively used, and while RavenDB has no problems handling large datasets, you may want to move old documents out of the way, to keep your active working set smaller.

An easy way to handle this is to mark document with `@expires` metadata field, so they will be automatically deleted after a certain time. But deleting data is a permanent operation, 
and not something to do just to make the task of the database easier. After all, regardless of the size of the data in question, it is the role of the _database_ to handle that.
RavenDB is perfectly happy with large datasets, including multi-terabyte databases. If you want to go beyond the amount of data that a single server can handle, you can use sharding
to spread the load across multiple servers (see <<sharding-in-ravendb>> for more details).

However, in many cases, you want to both keep the old data around, but it doesn't make _sense_ to keep orders data from three years ago in the same manner as your latest order. RavenDB
allows you to define an archiving time for your documents, which lets RavenDB aggressively optimize how it deals with those documents, assuming that they are rare accessed. 

Just like `@expires` and `@refresh`, you can set the archiving time using the `@archive-at` metadata field on your documents. And just like the other two features, you need to enable archiving
explicitly. You can do that in the RavenDB Studio by going to the `Settings` tab of your database, and then to the `Data Archival` section. Given that you just read about `@expires` and `@refresh`,
this should be very familiar to you by now and I'm going to skip the details here. Check the previous sections to get the full picture, since `@expires`, `@refresh` and `@archive-at` work in 
a very similiar manner.

When you store a document with the `@archive-at` metadata field set, RavenDB will automatically move that document to the archived mode when the time comes. What exactly does that mean? 
An archived document is still fully accessible, you can read it and modify it normally. However, there are a number of very important differences in how RavenDB handles archived documents:

* Indexes exclude archived documents by default, when a document is marked as archived, RavenDB will remove it from the index (as if it was deleted). This lets RavenDB keeps its indexes 
  smaller and more efficient. If an archived document is modified later on, it will be ignored by the index. You can also configure an index to exclude archive documents (the default), 
  include archive documents, or _only_ index archive documents.
* Subscriptions (discussed in <<batch-processing>>) also exclude archived documents by default. Just like with indexes, you can configure this behavior on a per subscription basis.
* Archived documents are stored on the disk in a compressed format, which reduces their disk usage significantly, at the cost of some CPU usage when reading them. We'll talk about the 
  compression mechanism in the next section.

The end result is the that archived documents are stored in a compressed form, aren't touched by indexes or subscriptions. That lets RavenDB discard it from the working set of the database,
so it will not take any memory from the server. They are stored in "cold storage" on the disk, and only touched when requested directly by id. This allows you to keep large amounts of old data 
around, without impacting the performance of your day to day operations.

Note that those three behaviors (ignoring during indexes, skipping in subscriptions and compressing on the disk) are the only differences in how RavenDB handles archived documents. In particular,
ETL processes or replication are _not_ impacted by the archived state of documents, they will be replicated or take part of ETL processes normally.

A typical use case for document archiving in an e-commerce system would be to archive orders documents that are over two years old. Those documents are rarely accessed, but you may need to get 
to them once in a while for auditing or other purposes. When you create an order document, you can set the `@archive-at` metadata field to the last day of the year, two years in the future. 
For example, `"@archive-at": "2028-01-01T00:00:00.0000000Z"` for an order created today (November 2025). That way, at the start of 2028, RavenDB will automatically archive all the documents, 
removing it from indexes.

.Selecting the archive date has an impact on your system
****
You can simply set the archive date to be two years from the creation date of the document. That would mean that the archiving process will be spread evenly over time. In practice, that isn't
usually how businesses operate. Most businesses have a yearly cycle. It is very common to need to want to search over data for the last year or the previous one.
For that reason, it is often better to set the archive date to be the same for all documents in a given year. For example, for all orders created in 2025, set the archive date to be 
`2028-01-01T00:00:00.0000000Z`. 

That is something that you want from a business perspective, but it also has technical advantages. When the new year rolls by, RavenDB now needs to archive all the documents from two years ago.
That can be a significant amount of data, and RavenDB will handle that in the background. Note that archiving, just like `@expires` and `@refresh`, happens on the primary node in a cluster, 
and the changes are replicated to the other nodes. And like expiration and refresh, RavenDB is going to _start_ archiving the documents at the specified time, but it may take some time to 
complete the process. 
****

Following the archiving in Jan 2028, queries on orders for a customer, will only consider the documents from 2026 and 2027. If you need to read an archived order, you can do that directly by id.
Alternatively, you can create a dedicated index that includes archived documents, to be able to query them as well. The `"Orders/Archived"` index is configured to only index archived documents,
and it is queried only on very specific scenarios, such as auditing or generating reports over old data.

Using the example above, with the archive date set to the start of the year, that index for archiving documents will only need to index documents once a year, when the archiving process runs.
I'm jumping ahead a bit, since we'll cover indexing in depth in <<indexing-in-ravendb>>, but I wanted to explain how archiving and indexing interacts. This `"Orders/Archived"` index will run 
once a year, and if (as expected) there are no queries on this index, RavenDB is able to idle the index completely. In other wrods, the archive index will consume no resources from the system
while there are no queries on it.
