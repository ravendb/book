## Beyond mere documents: Attachments, Counters, Times Series and Revisions

RavenDB is all about documents, everything in RavenDB revolves around them. And documents in RavenDB are JSON objects that can
be as complex and large as you want them to be.footnote:[Well, actually... documents in RavenDB are limited to about 2GB in size,
and the largest record document that _I_ personally saw in RavenDB was ~800MB. That is _not_ recommended, see <<document-modeling>> 
for more details on that.]
JSON is awesome, but it isn't always the best format to store your data. Luckily, RavenDB comes with several additional options to 
handle most common scenarios.

### Attachments

Binary data is not well suited for JSON. You _can_ use BASE64 to encode the value (at 25% overhead in storage), but that is rarely
a good idea unless they are very small. Many applications needs to handle large binary values, a profile picture or an uploaded PDFs
are two such common examples. 

RavenDB offers the attachments feature to handle this scenario. Conceptually, you can think about attachments in RavenDB in the same
manner you do attachments in email. Let's see how this works first, and then discuss what is actually going on behind the scenes. In
<<storing-attachments>> you can see how we create a new `Invoice` document and add a PDF file to it.

[[storing-attachments]]
.Storing an attachment in RavenDB
[source,csharp]
----
using (var session = store.OpenSession())
{
    Invoice invoice = CreateNewInvoice(out string pdfInvoice);  <1>
    session.Store(invoice);                                     <2>
    using var pdfStream = File.OpenRead(pdfInvoice);            <3>
    session.Advanced.Attachments
        .Store(invoice, "invoice.pdf", pdf,"application/pdf");  <4>
    session.SaveChanges();                                      <5>
}
----
<1> Here we create the invoice instance and get the `pdfInvoice` filename. This piece is not related to RavenDB.
<2> Storing the new invoice in the session (same as we did in the previous chapter).
<3> Open a `Stream` from PDF file, to pass to the `Attachments.Store()` method.
<4> Store the attachment stream (with a name and content type) into the session. Does _not_ call to the server.
<5> Atomically stores both the new invoice and its attachments into the database.

In <<storing-attachments>> you can see the basics of storing a new attachment in RavenDB. As the name suggests, we _attach_ the stream
to an existing document. Attachments do not exists on their own and are always associated with a docuemnt. 
As a result, deleting the document will also delete all its attachments. You cannot have a free-standing attachment.footnote:[You can 
have a document just to hold an attachment, of course]

In the Studio, you can see the attachments for a document on the right hand side, as you can see in <<attachments-in-studio>>.

[[attachments-in-studio]]
.The `invoice.pdf` attachment on the `Invoice` document in the Studio
image::./Ch03/img01.png[]

As you can see, in the RavenDB Studio we have a dedicated pane for attachments. You can click on the `invoice.pdf` in 
<<attachments-in-studio>> to download the file. We talked about document metadata in the previous chapter, and here is a good 
chance to see how RavenDB makes use of it in <<attachment-metadata>>.

[[attachment-metadata]]
.The metadata element in the `Invoice` document after we attached a file to it.
[source,json]
----
{
    "@metadata": {
        "@attachments": [                                               <1>
            {
                "Name": "invoice.pdf",                                  <2>
                "Hash": "SszdDSioWjvoO7ygOIGz52srIoicf4slUMy/js2WQKc=", <3>
                "ContentType": "application/pdf",                       <4>
                "Size": 258642                                          <5>
            }
        ],
        "@collection": "Invoices",
        "Raven-Clr-Type": "Tryouts.Invoice, Tryouts",
        "@change-vector": "A:16-woIsp5F3M0m00sjsTKlJ0g",
        "@flags": "HasAttachments",                                     <6>
        "@id": "invoices/1-A",
        "@last-modified": "2025-09-30T06:18:26.2639106Z"
    }
}
----
<1> The `@attachments` array holds all the details about the attachment on this document.
<2> The name of the attachment, must be unique _within_ this document. In other words, two documents can each have `invoice.pdf` 
    attachment with no issues.
<3> Cryptographic hash of the attachment - used for de-duplication of data, discussed more later.
<4> The content-type of the attached file - this is not used by RavenDB directly, except to set the `Content-Type` header when 
    downloading the file.
<5> The size of the attachment in bytes.
<6> RavenDB internal flags - indicating that this document has an attachment.

<<attachment-metadata>> shows a _lot_ of information about attachments. At first glance, this is just the metadata about the 
file we attached. On closer inspection, there is a wealth of information here that shows what happens behind the scenes.
A document has an array for `@attachments`, and natually you can have multiple attachments for the same document. 
Attachments names are scoped to the document that you attach them to. So you can have two `Invoice` documents each with their own
`invoice.pdf` file. In the same document, however, attachment names are unique.

In the previous chapter, we created the `Northwind` database and seeded that with the sample data. The sample dataset contains

[[employee-image]]

The attachment metadata also includes all the information you need _about_ the attachment, expect its content. You can access the
`ContentType` or the `Size` of the attachment directly from the document metadata, without needing to make a separate remote call
to get those details. There is also the `Hash` element, which holds the cryptographic hash of the attachment's contents. 

[IMPORTANT]
.Attachments de-duplication
====
RavenDB automatically handles de-duplication for attachments when you add them to the database. This is done by computing a cryptographic
hash of the attachment's content and seeing if we already have that stored. If the value is already stored, we'll just reference the 
stored data, rather than needing to hold duplicate copies. This is handled completely transparently to you and requires no attention.
You _can_ make interestting use cases using this information, however.
====

#### Working with attachments

Beyond just storing attachments, we can also do various (server-side) operations on them, such as:

* `Rename` - change the name of the attachment to a new one (no need to re-upload the file) on the same document.
* `Move` - move the attachment from the source document to _another_ document (potentially renaming along the way).
* `Copy` - associate already existing attachment on a document with another document (no data is duplicated).
* `Delete` - delete the attachment from the document (if there are no other documents referencing the attachment, it will be remove).

A good example of how you make use of attachments in shown in <<copying-attachments>>. Like all such calls in the session,
calling `Copy`, `Move` or `Rename` does not actually perform the work but register it in the session to be executed as a single
transaction when `SaveChanges` is called.

[[copying-attachments]]
.Copying the default profile image when we create a new user
[source,csharp]
----
using (var session = store.OpenSession())
{
    User person = new User("Oscar", "Arava");
    session.Store(person);
    session.Advanced.Attachments.Copy(          <1>
        "users/default", "default-image.png",   <2>
        person.Id, "profile-image.png");        <3>
    session.SaveChanges();                      <4>
}
----
<1> Copy the attachment one document to another (without going through the client).
<2> The source docuemnt and attachment name.
<3> The destination document and attachment name.
<4> Actually sending the `Copy` command to the database for execution. 

<<copying-attachments>> shows creation of a new user and attaching the default profile image to it. Note that we don't need to
download & upload the file to create it. Furthermore, we take advantage of RavenDB's attachment de-duplication to have a single
copy of all the default profile images, across however many numbers of users we have.

.Attachments vs. BLOB
****
If you have worked with binary data with other databases, you are likely familiar with the concept of BLOB (binary large objects)
columns. RavenDB's attachments are similar in concept, but quite different when you look in depth. The actual data for the attachment
isn't stored alongside the document's data. In fact, given that a single copy of the attachment can be associated with many documents, 
it _can't_ be stored inline. 

To read the content of the attachment, you _must_ explicitly load it. There is no option for doing something like `SELECT * ...` and
accidently reading very large values. 
****

#### Reading attachments

The simplest way to read an attachment is shown in <<reading-attachment-content>>. We get back an `AttachmentResult` which holds the
attachment's `Details` and you can read the actual contents from the `Stream`.

[[reading-attachment-content]]
.Reading the attachment concept and writing to the output
[source,csharp]
----
using AttachmentResult result = session.Advanced.Attachments
    .Get("people/1-A", "profile-image.png");
result.Stream.CopyTo(outputStream);
----   

Note that you should dispose the `AttachmentResult` you get from the opertion when you are done with it. You can also use the `Get()`
overload that accepts a number of `AttachmentRequest` values, to download multiple documents in a single remote call.
You can also read a particular range of data from the attachment using the `GetRange` method. This allows advanced scenarios on your
end if you are working with large attachments.

[NOTE]
.RavenDB's attachments has no size limit
====
Attachments in RavenDB have no size limits. You can store 10GB of video file inside of RavenDB (and stream it out using 
the `GetRange` method) without any issues.

_Documents_ are limited in size in RavenDB (to about 2GB or so), and the attachment names and metadata are stored in the document itself.
You should avoid having a "dumping ground" with a single document holds a _lot_ (tens of thousands) of attachments. It is better to have
a separate document per attachment if this is the case.
====

#### Attachments storage

RavenDB doens't do _anything_ with the attachment data. It simply holds them for you. This is in sharp contrast to storing JSON data, where
RavenDB expose a lot of operations on documents and store them internally in an optimized format for its needs.
Attachments are just stored. And this has important implications for your usage. 

Consider storing a large `data.txt` file as an attachment. RavenDB will simply store that. If you were to compress using `GZip` or `Zstd`
you'll likely get a far smaller file, which you can them upload as an attachment (`data.txt.gz`, for example). Usually storage space on 
database servers is _expensive_ and you should attempt to reduce the amount you use needlessly.

RavenDB also supports the notion fo retiring attachments (sometimes called remote attachments). That allows you to set a specific period
of time before RavenDB will move the attachment's content to object storage (S3 or any compatible API backend) to store the attachment's
contents. This is done in a manner that is completely transparent to your application. 

After retiring an attachment to S3, you can still call to `Get()`, `GetRange()`, etc as you previously did. RavenDB will take care of 
proxying the request to the appropriate location. A major benefit of this is that you can have a transactional operation on both documents
and attachments, then RavenDB will push the data to S3 (and transparently proxy as needed for reads) behind the scenes.
See the online documentation for the full details on how to confiure and run this option.

[WARNING]
.Indexing attachments contents
====
We'll cover indexing in RavenDB in <<indexing-in-ravendb>>, but it is important to note that you _can_ index attachments' contents. 
However, if you'll retire attachments to object storage, you'll _not_ be able to index the remote attachments. In practice, you'll
usually only index small attachments and thus aren't usually candidates to retire to object storage.
====

### Counters

Counters are a very simple concept, it is just a named 64 bits signed integer that can be attached to a document. 
In the sample data (which you can find in the `Northwind` database we created in the previous chapter) you can look at the `Products`
collection to see usages of counters. You can see that in <<counters-usage>>.

[[counters-usage]]
.Counters usage in the `Products` collection for ranking products
image::./Ch03/img03.png[]

In <<counters-usage>> we were having fun, using emojis as the counter names. The idea is that we count how many times a product was
rated one to five stars, with a dedicated counter to each rating.

Why would you want to use a Counter compared to a simple numeric property on the document? Let's consider the scenario
of starring a product. You can use counters for this, as in <<counters-usage>>, or a property on the document. The key difference
between the two is that counters allow you to increment or decrement a counter in a concurrent and distributed fashion safely.

<<increment-counter>> shows how we can use the RavenDB client API to increment a counter on a document.

[[increment-counter]]
.Creating a document and incrementing a counter vs. incrementing a property vs. patching the document
[source,csharp]
----
using (var session = store.OpenSession())
{
    var page = new Page("/index.html");         <1>
    session.Store(page);
    session.SaveChanges();
}

using (var session = store.OpenSession())
{
    session.CountersFor("pages/1-A")
            .Increment("Visits");               <2>
    session.SaveChanges();
}

using (var session = store.OpenSession())
{
    var page = session.Load<Page>("pages/1-A");
    page.Visits++;                              <3>
    session.SaveChanges();
}

using (var session = store.OpenSession())
{
    session.Advanced.Defer(new PatchCommandData("pages/1-A", 
        null, new PatchRequest                  <4>
        {
            Script = "this.Visits++;"
        }));
    session.SaveChanges();
}
----
<1> Create a `Page` document.
<2> Increment the `Visits` counter (creating it along the way) on the `pages/1-A` document.
<3> Loading the page, incrementing the `Visits` property and saving the changes back to the database.
<4> Using patching to increment the `Visits` property on the server side.

<<increment-counter>> shows all the ways that we can record a visit to a page. The first is using a counter and the second is using
a property on the document. What is the difference between the two?
To increment a counter, we don't need to load the document, and RavenDB will take care of merging concurrent increments to the same
counter (even if they happen on different nodes). 

.Counters are created on the fly
****
A counter is created the first time you call `Increment` on it, there is no need to create a counter before you can use it. 
This make it very useful to use dyanmic names for the counter to record information (for example: `visits/os:macosx`, 
`visits/browser:edge`). If you go that route, remember that the list of counter names is stored in the document metadata and 
that you don't want that to get out of hand. Dozens to low hundreds counters on a document is okay, thousands or more probably require
a rethink on how you model the data.
****

On the other hand, to increment the `Visits` property on the document, you must load the document first, increment the property then
save the _entire_ document back to the database. There is also the option of using _patching_, the last example in <<increment-counter>>,
we'll discuss patching documents in more dpeth in <<ravnedb-client-api>>. For now, just know that this allows you to do document 
modifications completely on the server side.

Consider the scenario of two concurrent visits to the same page. How would that work? If we use the option of loading the document
and modifying the property, we've problem of losing one of those updates. If we use the patch approach, if we talk to multiple nodes
at the same time, we run the risk of a conflict between them. 

.Decrementing a counter
****
RavenDB doesn't offer a `Decrement` operation on counters. You can pass a negative value to `Increment` in order to decrement
the value.
****

Counters solves this problem completely, you don't need to read the previous value, and RavenDB will merge concurrent writes both
in a single node and distributed across the cluster.

Following RavenDB's design philosophy, you can `include` a counter when you load a document, as you can see in <<reading-counters>>.
Meaning you need a single remote call to fetch both pieces of infomration.

[[reading-counters]]
.Reading a document & its counter in a single roundtrip to the database
[source,csharp]
----
var page = session.Load<Page>("pages/1-A", includes =>
    includes.IncludeCounter("Visits"));
long visits = session.CountersFor(page).Get("Visits") ?? 0;
----

Similar to attachments, we store information _about_ the counters associated with a document in the document's metadata. 
The actual counters' data is kept separate from the document itself.

[[counters-metadata]]
.The metadata RavenDB keeps about counters in the document's metadata
[source,json]
----
{
    "@metadata": {
        "@collection": "Pages",
        "@counters": [                                      <1>
            "Visits"
        ],
        "Raven-Clr-Type": "Tryouts.Page, Tryouts",
        "@change-vector": "A:34-woIsp5F3M0m00sjsTKlJ0g",
        "@flags": "HasCounters",                            <2>
        "@id": "pages/1-A",
        "@last-modified": "2025-09-30T18:39:19.8423899Z"
    }
}
----
<1> The counter names in this document
<2> RavenDB internal flags noting that this document has counters

.Counters cannot overflow or underflow
****
Counters are 64 bits signed integers (`long` in C#/Java/C, etc). If an increment operation would cause the value to overflow
or underflow, an exception will be raised. In practice, this is not something that you usually have to concern yourself with, but
it is important to note that you are protected from this issue.
****

#### Deleting counters

RavenDB offers the `Delete` operation on counters, as you can see in <<delete-counters>>.

[[delete-counters]]
.Deleting a named counter on a document
[source,csharp]
----
using (var session = store.OpenSession())
{
    session.CountersFor("pages/1-A")
            .Delete("Visits");
    session.SaveChanges();
}
----

Deleting counters is expected to be rare operation, and it has important interactions with concurrent `Increment` when working in a
distributed environment. Consider the case of two concurrent requests to two separate nodes in the cluster. One to `Delete` the
`Visits` counter on `pages/1-A` and the other to `Increment` the same counter. What will happen?

In this case, the `Increment` wins and the value will be retained. Some of the previous increments (before the `Delete`) that haven't
been pushed to the cluster may be lost, however. In general, users are expected to avoid mixing `Delete` and `Increment` operations.
That isn't a case of undefined behavior leading to nasal demons, mind. The behavior is well defined and tested, it is simply complex
and involved a lot of distributed state and concurrency. 

### Time Series

Time Series is used when you care about a value and the way it changes over time. The classic example is your heartrate. My 
_current_ heartrate, for example, is currently at 66 BPM. This doesn't tell you much about me or my health. A doctor looking at heartrate
over a period of 24 hours, on the other hand, can probably tell a lot about the health of the patient. Another common example is currency
exchange rate. If the USD/EUR is at 0.99 at the moment, that is interesting. But you can derive a lot of interesting information from 
looking at how this value changed over time.

RavenDB supports time series natively, and it stores them using an optimal format to reduce storage costs and improve queries efficeincies. 
In the sample dataset (check the `Northwind` database we created in the previous chapter), we have time series available on the `Employees`
and `Companies` collections. You can see what this looks like for `employees/1-A` in <<time-series-in-studio>>.

[[time-series-in-studio]]
.Time Series pane for the `employees/1-A` document
image::./Ch03/img04.png[]

You can see the count of values (120) and the range of values for the `HeartRates` time series (in this case, a single day). If you'll click
on the eye icon, you'll be able to see the actual values, showing in <<time-series-details>>.

[[time-series-details]]
.Detail view for the `HeartRates` time series for `employees/1-A`
image::./Ch03/img05.png[]

<<time-series-details>> shows a lot of interesting details. You can see that each value in a time series has a `Date`, a `Value` and a `Tag`.
The `Date` is the instnace in time when this value was recorded, the `Value` the `BPM` (beats per minute) in that instance and the `Tag` is 
a way to provide some additional information about that particular value.

.Time Series tags
****
Each time series value has a tag associated with it. This tag is just free text that you can add. It's purpose is to record information
about the value itself. In the case of <<time-series-details>>, you can see that the tag records that the data came from `watches/fitbit`.
Another user may have that data provided through `watches/apple-watch`, etc.

It is recommended that the tag will be short and repetitive. A document ID that contains information about the source for that particular 
datum is best. In most cases, the data source doesn't change often, so you'll naturally get good results. The reason this matters relates
to the way RavenDB actually stores this information, and is discussed in more depth later in this chapter.
****

You'll usually not care about individual values in a time series, you care a lot more about all the values together. <<time-series-query>> 
shows how you can run a query on a time series and get aggregated information about it. <<time-series-graph>> shows the results of this
query.

[[time-series-query]]
.Getting average & max heart rate every 15 minutes from `employees/1-A`
[source,sql]
----
from 'Employees'
where id() == 'employees/1-A'
select timeseries(from 'HeartRates' group by 15m select avg(), max())
----

[[time-series-graph]]
.Chart view for the query in <<time-series-query>>
image::./Ch03/img06.png[]

Time Series are associated with a document, just like attachments and counters. You can see how we append a value to a time series on a
document in <<time-series-append>>.

[[time-series-append]]
.Appending a value to a time series
[source,csharp]
----
using (var session = store.OpenSession())
{
    session.TimeSeriesFor("pages/1-A","DailyUsers")
        .Append(DateTime.Today, [2351], tag: "google/analytics");
    session.SaveChanges();
}
----

In <<time-series-append>> you can see that we append a value for today to the `DailyUsers` time series on `pages/1-A`. Like counters, there
is no time series creation step. The time series for a document is created on the first append of a value. You can also see that we can
append mulitple values to a particular time in a time series. In <<time-series-append>> we add a single value, but you can add up to 32
values to a time series. 

The `Append` call accepts a `DateTime` as its first argument. <<time-series-append>> pass `DateTime.Today` as the value, but it is
important to understand that RavenDB time series operate _only_ on UTC time. All values are converted to UTC when you append it.
RavenDB offers the `offest` option when querying the time series, to allow you to match your time zone offeset if needed.

.The value of a time series - array of `double` values  
****
We can append up to 32 values to a time series at a particular point in time. Those values are of type `double`, more preciesely, 
double precision floating point IEEE 754 numbers. We recommend that you'll always pass the same number of values on each call, but it 
isn't _required_. If you pass 3 values in one call and 1 in the next call, it will just work for RavenDB. It is often a pitfall for 
clients that process the data and expect each entry in the time series to have the same number of values.

You cannot pass `NaN` as a value to the time series, RavenDB will reject such values. 
****

What happens if we `Append` _another_ value with an already existing date? <<time-series-overwrite>> explores RavenDB's behavior in
this case.

[[time-series-overwrite]]
.Overwriting an existing value
[source,csharp]
----
using (var session = store.OpenSession())
{
    session.TimeSeriesFor("pages/1-A","DailyUsers")                     <1>
        .Append(DateTime.Today, [4381], tag: "google/analytics");
    session.SaveChanges();
}

using (var session = store.OpenSession())
{
    var series = session.TimeSeriesFor("pages/1-A", "DailyUsers")
        .Get(DateTime.Today.AddDays(-1), DateTime.Today.AddDays(1));    <2>
    foreach (var item in series)
    {
        // prints: 9/30/2025 9:00:00 PM - 4381
        Console.WriteLine(item.Timestamp + " - " + item.Value);
    }
}
----
<1> Overwrite an existing value by sending new values for existing date in the time series
<2> Reading a range of values from the time series and printing it

In <<time-series-append>> we overwrote the value from <<time-series-append>> by sending new values for an existing time. Note that 
this time needs to be _exactly_ the same time value (down to the millisecond). <<time-series-append>> also shows how we can read 
a range of values from a time series and print it out.

The `include` feature of RavenDB also support time series, as you can see in <<including-time-series>>.

[[including-time-series]]
.Loading a document and a time series range in a single remote call
[source,csharp]
----
var page = session.Load<Page>("pages/1-A", include =>
    include.IncludeTimeSeries("DailyUsers", 
        DateTime.Today.AddDays(-1), 
        DateTime.Today.AddDays(1)));
var series = session.TimeSeriesFor(page, "DailyUsers")
        .Get(DateTime.Today.AddDays(-1), DateTime.Today.AddDays(1));
----

When we read from a time series, we always need to pass a start & end markers. This is because time series in RavenDB are design
to hold a _large_ number of values. We have tested RavenDB with billions of entries in the time series, see more about the storage
aspects of time series later in this chapter. You can usually not read the entire time series (nor does it make sense), so the ability
to request all values within a range allow you to fetch a reasonable chunk for processing or viewing.

.Date values in time series
****
The date value in time series is _always_ in UTC and is using millisecond granularity. 
The `DateTime` type in C# can actually go to lower granularity than millisecond, but RavenDB will truncate all dates to 
millisecond granularity.
****

Like attachments and counters, you can see in <<time-series-metadata>> how RavenDB records the existence of a time series in a document.

#### Querying time series

We saw in <<time-series-query>> previously how we can query time series. We'll cover queries in far more depth in <<querying-in-ravendb>>
but I want to cover some of the basics of what you can do with time series before we get any further.

All time series queries start by first finding the relevant document and then querying over the appropriate time series and range.
<<simple-time-series-query>> shows how you can query a time series and gets it raw values. You can copy the query in the RavenDB
Studio Query page (in the `Northwind` database) to execute it and see the results.

[[simple-time-series-query]]
.Get raw time series results in a date range from `HeartRates` on `employees/1-A`.
[source,sql]
----
$start  = '2020-05-16'              <1>
$end    = '2020-05-18'

from 'Employees'                    <2>
where id() == 'employees/1-A'       <3>
select timeseries(                  <4>
    from 'HeartRates'               <5>
        between $start and $end     <6>
    where Tag = 'watches/fitbit'    <7>
)
----
<1> The parameters for the query.
<2> Which collection we are targeting.
<3> Filtering the documents to find.
<4> The actual time series query expression to run for each document.
<5> Which time series to select from.
<6> Defining the range that we scan in the time series
<7> Filtering the raw results from the time series in the selected range.

<<simple-time-series-query>> shows off quite a few features in a concise form, see the comments immediately following it. I'm
not going to cover everything about time series queries. If you are interested in the full details, check the online documentation.
Note that we are filtering the time series results by tag, so we'll only get entries that came from `watches/fitbit`. You can also
filter on the raw values (using `where Values[0] > 70`). 

Note that filtering on the time series results, you'll be _scanning_ through the results. If you are going through a large range, 
that can take a while. 

When querying on time series, <<simple-time-series-query>> shows querying by id. You can also use a query that would return 
multiple results, such as `where Address.city = 'London'`. In this case, you'll get a separate time series result for each of the 
match documents of the top query.

Usually when querying over a time series, you aren't interested in the raw values, but aggregated to a given time period. We 
saw that in <<simple-time-series-query>>, where we grouped the results on 15 minutes boundary. Let's see another such
query and discuss that in detail. In this case, we are querying over the `StockPrice` time series in the `Companies` collection.

[[aggregate-time-series-query]]
.Get aggregated stock price details for the first half of 2020, on a monthly basis, for `companies/88-A`.
[source,sql]
----
$start = '2020-01-01'
$end = '2020-06-01'

from 'Companies'
where id() == 'companies/88-A'
select timeseries(
    from 'StockPrices' between $start and $end
    group by '1 month'                                  <1>
    select avg(), min(), max(),                         <2>
           first(), last(), sum()
)
----
<1> Grouping the results by 1 month.
<2> Selecting which aggregation functions to perform on the results.

<<aggregate-time-series-query>> shows off a few interesting details. When you run this query in the studio, you'll see the results
in <<aggregate-time-series-query-output>>. You can see that we select multiple aggregation options for the data, and that the query
grouped the data on a monthly basis. 

[[aggregate-time-series-query-output]]
.Chart view of the <<aggregate-time-series-query>> query.
image::./Ch03/img07.png[]

You can group by milliseconds, seconds, minutes, hours, days, months, quarters and years. For example, you can group by `6 hours` or
`30 seconds`. The interesting thing about how RavenDB deals with aggergations and `group by` for time series is when you need to 
aggregate over large amounts of data with coarse granularity.

Consider a use case where we record heartrate on a per second basis, and needing to visualize that to the user as
average, highest and lowest heart rate on an hourly basis for the past week. Let's compute the number of results we have to go through. 
A week has a total of 604,800 seconds, so that is the number of results we have. Because we output on an hourly basis, we have
a total of 168 hours in a week. You can see the query in <<aggregate-time-series-week>>.

[[aggregate-time-series-week]]
.Aggreggate heart rates in hour granularity for the past week.
[source,sql]
----
from 'Employees'                    
where id() == 'employees/1-A'       
select timeseries(                  
    from 'HeartRates'               
        between $weekAgo and $now
    group by 1h                     <1>
    select avg(), min(), max()      
)
----
<1> Grouping in 1 hour granularity.

How does RavenDB processes the query in <<aggregate-time-series-week>>. It isn't going to run through the 604,800 entries we have. 
Internally, RavenDB stores the time series entires in segments, and it is able to condense the results of many entries into a 
single segment. The actual compression ratio depends on the exact data you have. In this case, I was able to fit 608,400 time 
series entries in 378 segements. With about 1,600 entries per segment. In terms of raw size, that is under 4MB in size. 

RavenDB aggregations are able to take advantage of these low level storage details. Each segment already stores the aggregated values
for each segment and the aggregation process can skip going through 604,800 entries and deal with aggregation on the 378 segments. 
In other words, you can do _fast_ aggregations without paying the cost for them.

#### Deleting time series data

You can delete data from a time series by specifying a specific time series entry to remove by its date or by specifying a range
and removing all the entires included in it. If you removed all the entries in the time series, RavenDB will delete the time series
from the document. You can see how this looks like in <<deleting-time-series>>.

[[deleting-time-series]]
.Deleting data from a time series
[source,csharp]
----
session.TimeSeriesFor("pages/1-B", "DailyUsers")
    .Delete();                                          <1>

session.TimeSeriesFor("pages/1-B", "DailyUsers")
    .Delete(DateTime.Today);                            <2>

session.TimeSeriesFor("pages/1-B", "DailyUsers")
    .Delete(                                            <3>
        DateTime.Today.AddDays(-7), 
        DateTime.Today.AddDays(-1));                     
----
<1> Deleting the entire time series (by deleting all its values).
<2> Deleting a specific time series entry at the given date.
<3> Deleting all the time series entries from a week ago to yesterday.

In a similar fashion to the counters, mixing `Delete` and `Append` is likely to produce unexpected results. If you `Delete` an entire
time series (or even just a range) and you have concurrent `Append` to the time series (or the range being deleted), the `Append` will
take precendance, but some of the values may be lost. It is the user responsability to ensure that this is handled properly.

.Optimizing time series storage requirements
****
All the entries inside a time series are compressed using Gorilla compression.footnote:[Gorilla compression is a time series compression
method from Facebook.]

The reason this matters enough to cover in this book is that the compression format benefits greatly from predictability. Let's assume
you wish to record your heart rate every minute. In practice, one value will be recorded in `12:22:00.8027074` and the next will be in 
`12:23:01.3754696`, etc. It is more efficient for RavenDB if you'll truncate those values to `12:22:00` and `12:23:00`.
That way, it can more easily predict the values and use less bits to store them. 

In the same sense, if the values you are storing are mostly the same, we can compress them more efficeintly. Consider what level of
accuracy you need from your values. For example, for heart rate, you can truncate to a single decimal digit. 

In general, if you need to store large amount of information in a time series, those considerations can save you a _lot_ of space.
****

### Time Series rollup & retention policies

RavenDB time series are meant to store _large_ amount of data. We have tested the implementation with billions of data points in 
a single time series. It is easy to get to big sizes with a time series. Consider a simple scenario of keeping track of a user's
heartrate on a per second basis. That means that you'll record 31,536,000 entries per year. Assuming a good compression ratio, 
that should take about 250MB or so.

250MB is a reasonable size to keep, but what happens if I have a million users, and each one of them has a time series
like that? Now we are talking about 238 _terrabytes_ of data. And that is a horse of a different order of magnitude indeed.
You can store data of this size in RavenDB, but you'll need to go with sharded approach. See <<sharding-in-ravendb>> for more details
on that approach. 

Often enough, you don't need to keep the full data at the original granularity forever. In our heartrate example, we want to keep
the data at a second granularity for two weeks, then we need the data at per-minute granularity for another 6 months, then we can 
drop to per-hour level. RavenDB supports this using rollups and retention policies, as you can see in <<time-series-policies>>.

[[time-series-policies]]
.Defining rollup & retention policies for time series on the `Employees` collection.
image::./Ch03/img09.png[]

<<time-series-policies>> shows how we define the policies to do rollups (aggregate on a minute and hourly level) automatically as
well as the retention policies (when RavenDB will delete the data). The space savings this entails are quite huge. Going from per second
to per minute level, we reeuce the cost by an order of magnitude. And going to hourly basis reduce us by another order of magnitude. 
Storing a full year of data for a million users will now cost us tens of gigabytes, and not hundreds of terrabytes.

RavenDB allows you to define rollup and retention policy at the collection level only. All the time series on the collection share the same
rollup and retention policy.

#### How time series rollups work?

When executing a rollup, RavenDB create _another_ time series. In the case of the rollup policies we defined in <<time-series-policies>> 
and the `HeartRates` time series, we'll have: `HeartRates@Min` and `HeartRates@Hour` rollup time series. Those time series will store
the aggregated results for each of the values in the the source time series. 

In the case of the `HeartRates` time series, the `HeartRates@Min` rollup will contain the `Count`, `Min`, `Max`, `First`, `Last`, `Sum`
values each each minute. In other words, the rollup time series will have 6 "columns" for each of the values in the source time series. 
The `HeartRates@Hour` rollup will aggregate the values from the previous rollup, but here it will have teh same 6 aggregated values per
source value in the original time series.

Time series in RavenDB are limited to a maximum of 32 values per entry. Rollup time series also share this limitation, but because they
hold 6 aggregated values for each value in the source time series, RavenDB is unable to do rollups if you have more than 5 values in the
source time series.

.Time series have a lot of depths to explore
****
Time series in RavenDB have a lot of capabilities. I touched most of the core concepts in this chapter, but there is more depth
to explore. I would recommend looking into the online documentation to see what other options and capabilities you have avaialble.
****

#### Working with multiple values in a time series

Up to this point, we look into time series that mostly worked with a single value. RavenDB time series can hold up to 32 values for
a single point in time. Consider the case where we have a `Vehicle` document and we want to track its location over time. The code
in <<time-series-gps>> shows how we can do that.

[[time-series-gps]]
.Recording the current location of a vehicle using a time series with two values (lat/lng)
[source,csharp]
----
void RecordCurrentLocation(string vehicleId, float lat, float lng)
{
    using var session = store.OpenSession();
    session.TimeSeriesFor(vehicleId, "Location")
        .Append(DateTime.UtcNow, [lat, lng]);
    session.SaveChanges();
}
----

<<time-series-gps>> shows the natural extension of what we have done so far, simply passing an array of values to the `Append`
method. This will create a time series with the recorded locations of the car over time. You can then read the data and draw
the vehicle location over time.

One important thing to note about the code in <<time-series-gps>> is a very subtle detail. Typically, GPS coordinate are provided
to you as `float`. However, RavenDB time series values are always `double`. That _usually_ doesn't cause a problem, but there are
some cases where converstion from `float` to `double` result in a meaningful change in your domain. That is _very_ unlikely, but 
worth calling out explicitly. 

### Incremental Time Series

We previously used a RavenDB Counter to track the total number of visits on a page. It would be nice if we could also show the visits
on a time line. At first glance, it looks easy enough to do so usine time series. <<tracking-page-visits-time-series>> shows one such
attempt to use time series to track page visits over time.

[[tracking-page-visits-time-series]]
.Trying to track the number of page visits using time series - wrong approach
[source,csharp]
----
// Note: this is the _wrong_ way to do this, see the explanation below
session.TimeSeriesFor("pages/1-A", "Visits")
    .Append(DateTime.UtcNow, 1); 
----

The code in <<tracking-page-visits-time-series>> will record a count of one on every visit to the page. We can then get the total
visits per hour for the past week using the code in <<reporting-page-visits>>.

[[reporting-page-visits]]
.Reporting the hourly page visits for the past week using time series.
[source,sql]
----
from 'Pages'                    
where id() == 'pages/1-A'       
select timeseries(                  
    from 'Visits' between $weekAgo and $now
    group by 1h
    select sum()
)
----

The output we get from <<reporting-page-visits>> is _exactly_ what we want from this feature. It sums the number of visits from
the individual entries we appended to the time series. It also plays very well with the rollups faeture, allowing RavenDB to tally 
the visits to the right granularity that you want.

The problem with the code in <<tracking-page-visits-time-series>> is that is is *wrong*. It is wrong in a pretty subtle way, the
problem is what happens when you have two visits on the _same_ millisecond. In this case, calling `Append` on the same time will
be treated as an updated value, rather than incrementing the already existing value. If you'll use the approach in 
<<tracking-page-visits-time-series>>, you'll lose some visits when they happen on the same millisecond. That isn't what we want.
An ideal option would be to have the same behavior we have in counters, where we can increment a value concurrently and safely,
even when running in a distributed manner.

That is what _incremental time series_ are for. An incremental time series is a normal time series, whose name starts with: `"INC:"`.
You cannot `Append` to an incremental time series, but must always use `Increment`. On the client API, you'll also use 
`IncrementalTimeSeriesFor` instead of `TimeSeriesFor`. <<propertly-tracking-page-visits-time-series>> shows how this is done.

[[properly-tracking-page-visits-time-series]]
.Track the number of page visits using time series - properly
[source,csharp]
----
session.IncrementalTimeSeriesFor("pages/1-A", "Visits")
    .Increment(DateTime.UtcNow, 1);
----

In <<propertly-tracking-page-visits-time-series>>, if this is called concurrently on the same exact time (and even if the requests
are handled by different nodes), RavenDB will properly tally up all the values. In the sample dataset (in the `Norhtwind` database)
we use an incrmental time series to track the number of views in the `Products` collection using the `INC:Views` incremental time 
series.
<<querying-product-views>> shows how you can get daily view counts for a product for two months. And <<view-product-views>> shows
the output of the query.

[[querying-product-views]]
.Reporting daily product views from the sample dataset.
[source,sql]
----
$start = '2021-12-01'               <1>
$end = '2022-01-31'

from 'Products'
where Category = 'categories/1-A'   <2>
select timeseries(
    from 'INC:Views'                <3>
        between $start and $end     <4>
    group by 1d                     <5>
    select sum()                    <6>
)
----
<1> The date range we'll query each of the time series on.
<2> Return results for all the products in `categories/1-A` (Beverages).
<3> Selecting which time series we'll use - there is no difference here between incremental and standard time series
<4> Specifying the date range for the time series that we'll operate on.
<5> The grouping granularity (1 day, in this case).
<6> The aggregation to perform. For incremental time series, it is almost always `sum()`. 

[[view-product-views]]
.Query results for <<querying-product-views>>, both the full results and the chart for a single result
image::./Ch03/img10.png[]

In <<view-product-views>> you can see the output of a time series query that returns multiple results. For each result in the 
top level query, RavenDB executes the time series query and returns the results back to the caller. In this case, the result
of <<querying-product-views>> has 12 matching products, and each time series in it has 61 results.

.Incremental Time Series at the right granularity
****
In <<properly-tracking-page-visits-time-series>>, we used `DateTime.UtcNow` to record a visit to the page. That gives us
millisecond level precision on the number of visits to the page. It is almost _never_ useful to record stuff like page visits
with millisecond precision. We'll usually operate on those at maximum granularity of an hour, or maybe a minute. 

That being the case, it makes sense to call `Increment` using the minimal granularity that you will ever work with the data. 
In the case of page visits, that is probably a minute. So we'll use the following approach instead:

    var now = DateTime.UtcNow;
    var nowTrimmed = new DateTime(now.Year, now.Month, now.Day, 
                                  now.Hour, now.Minute, 0);
    session.IncrementalTimeSeriesFor("pages/1-A", "Visits")
        .Increment(nowTrimmed, 1);

This will record the values at the right granularity from the start, savings us more space and computation costs down
the line. Remember that you can always aggregate at a higher value (per hour, for example, if you recorded at a minute
granularity) at query time. 

Reducing the total number of entries is highly recommended.
****

Incremental time series are meant to solve a very specific problem, how to count values over time. In the same sense, counters
in RavenDB solves the same problem, for cases where you don't care about the time aspect. Like counters, you can also decrement
values by using a negative number when you call `Increment`. 

There is a a major difference between the incremental time series and counters that you should be aware of. Counters are using
signed 64 bits integer number as their code data type, while incremental time series are built on top of regular time series. 
As such, their core data type is an array of `double` values.
We haven't shown a code example of that, but you can absolutely send multiple values to incremental time series. 

Incremental time series also differs from standard time series in that they do not have a `tag` that you can use. 
What would be the `tag` for the same entry if two calls passed two different values? Instaed, RavenDB is using the `tag` internally
to manage the concurrent handling of incremental time series.

### Revisions

Certain classes of applications have very strict change control requirements for their data. For example, most medical, banking, 
payroll and insurance applications have strict “never delete since we need to be able to see all changes on the system” rules. 
One particular system I worked with had the requirement to keep all changes for a minimum of seven years.

With RavenDB, this kind of system is much easier. That’s because RavenDB has built-in support for handling revisions. 
Revisions are an immutable snapshot of a document, created either manually or using automatically by RavendB. That allows us 
to go back in time and look at the previous states of a document.

We'll start looking at manual handling of revisions. In the RavenDB Studio, open the `employees/1-A` document, and then click on
the `Revisions` tab on the right, shown in <<create-revision-pane>>.

image::./Ch03/img11.png[]

Clicking on `Create Revision` will create a revision with the current time. You can click on the revision to see its state, which 
would be identical to the current document. Go back to `employees/1-A`, update the first name from "Nancy" to "Max? and 
save the document. Now click on `Create Revision` again. You now have two revisions for the `employees/1-A` document.
You can click on either of them to see how the older revisions is named "Nancy" and the newer one is "Max". You can also click on the
`Compare` button to see the actuall difference between them, shown in <<revision-diff>>.

[[revision-diff]]

image::./Ch03/img12.png[]

RavenDB does not offer any option to modify revisions, they are intentionally immutable. You can create a revision yourself, using
the Studio or the client API, as shown in <<creating-revision-manually>>.

[[creating-revision-manually]]
.Creating a revision of a document using the client API
[source,csharp]
----
using (var session = store.OpenSession())
{
    session.Advanced.Revisions
        .ForceRevisionCreationFor("pages/1-A");
    session.SaveChanges();
}
----

In <<creating-revision-manually>> we are effectively doing the same as `Create Revision`. RavenDB will create an immutable snapshot
of the document's current state (see more below on attachments, counters and time series interaction with revisions, though).

The client API also allows to do more interesting things, such as creating a revision and modifying the document as part of the 
same transaction, as you can see in <<creating-revision-and-modifying-doc>>.

[[creating-revision-and-modifying-doc]]
.Modifying a document and creating a revision of its _previous_ state in a single atomic transaction
[source,csharp]

using (var session = store.OpenSession())

    var page = session.Load<Page>("pages/1-A");
    page.Title = "Hello World";
    session.Advanced.Revisions
        .ForceRevisionCreationFor(page);
    session.SaveChanges();
}
----

In <<creating-revision-and-modifying-doc>>, it doesn't matter whether we first update the document or called `ForceRevisionCreationFor`,
in both cases, we'll first create the revision (capture the _before_ state of the document) and then modify it.

Using `ForceRevisionCreationFor` to manually create revisions is viable for some use cases, where there are specific stages in which we
want to create revisions. For example, you may have a page in draft mode and not care about tracking revisions in that stage. But once it 
moved to published state, you want to keep a record of all changes.

It is far more common to want RavenDB to handle that for you, and you can configure RavenDB to autoamtically manage revisions for you.

.Revisions are compressed
****
When using revisions, you are likely to end up with a _lot_ of revisions. To reduce the storage cost of revisions, RavenDB compress
all revisions automatically for you. That is an internal detail, not externally exposed, but important for operations to know when 
using revisions.

RavenDB optimize the compression format based on the actual documents been compressed, generating the appropriate compression dictionary 
to get good compression ratio across many documents.
****

#### Revisions allow for time travel

A really nice capability that you get from having revisions is the ability to go back in time to a previous revision.
<<api-revert-doc>> shows how you can revert a page to its status in `2020-01-01`.

[[api-revert-doc]]
.Reverting a document to a past revision
[source,csharp]
----
using (var session = store.OpenSession())
{
    var pastPage = session.Advanced.Revisions
        .Get<Page>("page/1-A", new DateTime(2020,1,1)); <1>
    session.Advanced.Evict(pastPage);                   <2>
    session.Store(pastPage);                            <3>
    session.SaveChanges();                              <4>
}
----
<1> Fetch the page version as it was in `2020-01-01`.
<2> Force the session to evict (forget about) the revision instance.
<3> Store the `pastPage` as a _document_, so it will be saved back to the database.
<4> Actually save the old version of the revision as the new value of the document.

You can also perform a mass revert of documents from the RavenDB Studio. Go to `Settings` and then to `Document Revisions` and check
the `Revert Revisions` option as shown in <<revert-revision-btn>>.

[[revert-revision-btn]]
.The `Revert Revisions` button allows to mass revert documents to a previous state
image::./Ch03/img17.png[]

[[revert-revision-dlg]]

image::./Ch03/img18.png[]

<<revert-revision-dlg>> shows the options to do mass revert of docuemnts to a previous state, based on their revisions. You can specify
the time to revert the documents to and whether it applies to all documents or just to specific collections.

The `Time Window` option in <<revert-revision-dlg>> is interesting, from an implementation perspective. The use case for mass revert 
revision is that you'll want to go back to a previous time _recently_. The way `Revert Revisions` is implemented is that we scan through 
all the revisions in RavenDB and apply the first revision before the given date. The `Time Window` option determine how far back we should
look for matching revisions. The longer the `Time Window`, the deeper RavenDB will scan through all the revisions in the database to find
candidates to revert. 

As you can imagine, if you specify a very large `Time Window` or `Point in Time` that is in the far past, RavenDB may have to scan 
through a _lot_ of revisions. 

.Oppsies & point in time reverts
****
A key use case for the `Revert Revisions` is when you made an oppsie. You pushed a bad version to production and want to revert all 
changes made in the past day, or you run an update query on the wrong database, etc. `Revert Revisions` allows you to avoid a full
restore-from-backup scenario and revert the database state back to its previous state.

It does require that you'll have revisions already configured, of course, but it can be a true saver when the bell tolls for you.
****

#### Interactions of revisions with attachments, counters and time series

Revisions create an immutable snapshot of a document. Attachments, counters and time series are document extensions that are 
stored _separately_ from the document itself. That means that when you use those features in conjunction with revisions, there 
are a few things to keep in mind.

Revisions handle attachments seamlessly. Remember that attachments are stored internally in RavenDB based on
their cryptographic hash, for de-duplication purposes. Revisions are able to take advantage of that and simple create another
reference to the attachments' content in question. In other words, if you create a revision for a document with an attachment
and then update the attachment on the document, the revision's attachment will keep the _same_ attachment it had when it was 
created.

For counters and attachments, revisions handle things a bit differently. <<revisions-counters-time-series>> will make it easier
to explain what exactly is going on.

[[revisions-counters-time-series]]
.Metadata for a revision on the `products/75-A` document that has both counters and timeseries
[source,json]
----
{
    "@metadata": {
        "@collection": "Products",
        "@counters-snapshot": {                 <1>
            "⭐": 3832,
            "⭐⭐": 47,
            "⭐⭐⭐": 2488,
            "⭐⭐⭐⭐": 34989,
            "⭐⭐⭐⭐⭐": 48077
        },
        "@timeseries-snapshot": {               <2>
            "INC:Views": {
                "Count": 536,
                "Start": "2021-11-30T22:00:00.0000000Z",
                "End": "2022-02-17T06:31:30.0000000Z"
            }
        },
        "@change-vector": "A:8896-BdphfhgaDUaCc4sSTDq2Qw",
        "@flags": "HasRevisions, Revision, HasCounters, HasTimeSeries, ForceCreated",
        "@id": "products/75-A",
        "@last-modified": "2025-10-02T09:22:59.3194788Z"
    }
}
----
<1> Snapshot of the counter _values_ at the time of the revision creation.
<2> Snapshot of the timeseries _metadata_ at the time of the revision creation.

<<revisions-counters-time-series>> shows two different behaviors for revisions with counters and time series. For counters, we
record the _current values_ of the counters at the time the revision was created. This is simple to do because we can capture
the entire state of the counter in a single 64 bits number. We use the `@counters-snapshot` in the metadata to let you access
the counters stored state explicitly.

For time series, we face a far different problem. RavenDB's time series are meant to be _large_. It is common to have hundred of
thousands or millions of values in a single time series. If we were to duplicate all of that on each revision, we'll very quickly
run out of disk space. Instead of trying to duplicate the time series, we record in the time series snapshot the range of values
that existed in the time series at the time the revision was created.

In most cases, time series are added to in a time based manner. So new values in the time series will be outside the range you
have in the snapshot. In practice, it is fairly rare to want to deal with revisions on time series, and just being able to tell
what the range at the revision creation time is sufficent. Having said that, it is important to understand that the time series
data itself is _not_ maintained in the revision, unlike counters and revisions.

### Summary

In this chapter we went over some of the more interesting capabilties of RavenDB, beyond dealing with JSON documents. As much
as I like JSON, it isn't always the best option to store your data, and RavenDB isn't limited just to dealing with documents.

The idea is that we can provide dedicated support for storing binary data, time series and distributed counters. Instead of you
having to cobble together a solution, RavenDB has full fledged native support for them.

Attachments allows you to attach binary files to documents. RavenDB will store the data internally, managed de-duplication for 
the attachments so you'll only have a single copy of the data. You can also define retirement policy to move attachments from 
RavenDB out to object storage (S3 compatible) to reduce storage costs. Even after retiring the attachments to object storage,
RavenDB will allow you to keep using the RavenDB API to access them. Trasnparently hiding the actual storage location of the
attachment data and ensuring that you can have proper transactions composed of both files and documents.

Counters deal with the narrow task of counting values. They provide a cheap way to count values at high scale 
without worrying about concurrency or distributed state. Unlike document properties that require loading before updating, counters can 
be incremented directly through client API methods. This eliminates read-modify-write requirement and make it cheaper to work
with counters.

Time series allow you to efficiently record changes to values over time. RavenDB can handle time series with billions of entries 
and once stored, you can query, aggregate and filter the time series data easily. You can also define rollup and retentions policies
to reduce the amount of data that you need to hold on to. Time series are a great fit for a number of domains, such as medical, 
finance and spatial. 

Incremental time series combine the benefits of counters and time series, allowing you to concurrently increment values at 
specific points in time. RavenDB will then take care of dealing with both concurrency handling and dealing with distributed
state so you'll end up with the right final tally without needing to concern yourselves with the details.

Finally, Revisions allow you to create immutable record of changes to your documents. This helps great when you _must_ have a proper
audit log of changes in your system, including proper verification that the data cannot be modified behind your back. Revisions are
also useful to expose "looking back" features to your users, as well as implementing revert feature in your application.

In this chapter, we explored the more esoteric types of data that you can work with in RavenDB. The reasons we call RavenDB a multi
model database, rather than just a document database. In the next chapter, we are going to move back to JSON documents and all the
ways you can use RavenDB's advance features in your application to make your system better.
